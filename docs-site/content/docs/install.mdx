---
title: Install libassimp
description: Add the package, pick an entry, and let a bundler or a worker find the binary.
---

libassimp is one package with three entries. Each entry ships its own
WebAssembly binary and its Emscripten glue beside the JavaScript, and loads
them on the first conversion.

```bash tab="npm"
npm install libassimp
```

```bash tab="pnpm"
pnpm add libassimp
```

```bash tab="yarn"
yarn add libassimp
```

Node.js 22.14 or newer, and the package is ESM-only: `require('libassimp')`
throws with the message `libassimp is ESM-only; use import("libassimp") from
CommonJS`. Use a dynamic `import()` from CommonJS code.

## Pick an entry

| Import               | Reads                  | Writes                           |
| -------------------- | ---------------------- | -------------------------------- |
| `libassimp`          | every importer         | every exporter                   |
| `libassimp/importer` | every importer         | glTF, GLB and assimp's JSON dump |
| `libassimp/exporter` | glTF, GLB, USD and VRM | every exporter                   |

The API is identical on all three; only the accepted `to` ids and the binary
size differ. [Choose an entry](/docs/guides/choose-an-entry) covers the
trade-off, and [How it works](/docs/how-it-works) lists every format each build
carries.

## Verify the install

Run one conversion rather than checking a version string: it proves the
JavaScript entry, glue, binary, importer and exporter all meet in this host.

<ConvertDemo>

```typescript
import { convert } from 'libassimp';

import { readFile } from 'node:fs/promises';

const bytes = new Uint8Array(await readFile('cube.obj'));
const { files } = await convert({ name: 'cube.obj', bytes }, { to: 'glb' });

console.log(files[0].name, files[0].bytes.byteLength);
```

</ConvertDemo>

Every instance also reports the tables it was compiled with:

```typescript
import { createAssimp } from 'libassimp';

using assimp = await createAssimp();

console.log(assimp.formats.import.length, assimp.formats.export.length);
```

```console
69 21
```

The two numbers are the extensions this build reads and the ids it writes. A
different pair means a different entry, not a broken install.

## Bundlers

The entry resolves its binary through `new URL('./wasm/…', import.meta.url)`,
which Vite and webpack 5 understand as an asset reference: the binary
is emitted into your build output and fetched from there, with no plugin and no
configuration. The Emscripten glue is imported through the same URL behind
`webpackIgnore` and `@vite-ignore` pragmas, so bundlers copy it instead of
pulling an Emscripten runtime into your application graph.

When your host serves the binary from somewhere else — a CDN, a hashed asset
directory, a Cloudflare Worker — pass its location:

```typescript
import { createAssimp } from 'libassimp/importer';

const assimp = await createAssimp({ wasmUrl: 'https://cdn.example.com/libassimp-importer.wasm' });
```

Each entry also publishes its binary on a subpath — `libassimp/wasm`,
`libassimp/importer/wasm`, `libassimp/exporter/wasm` — so a build step can copy
the exact file the entry expects. [Use in the browser](/docs/guides/use-in-the-browser)
covers fetching and caching it.

## Workers

The binaries are built without pthreads, so a worker needs no cross-origin
isolation headers and no extra bootstrap: import the entry inside the worker
and call it. A conversion holds the thread it runs on, which is the reason to
put one there.

## Hosts

Node.js 22.14, 24 and 26, plus Chromium, Firefox and WebKit, each have a job in
continuous integration. The binaries come from Emscripten 6.0, whose browser
floors are Chrome 91, Firefox 89 and Safari 16.4. The
[compatibility table](https://github.com/taucad/libassimp/blob/main/compatibility.md)
maps every claim to the job that proves it.
